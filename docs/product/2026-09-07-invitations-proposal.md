# הזמנות אישיות, מעקב עובדים, תגים ומשימות המשך — הצעת IA לאישור

תאריך: 2026-09-07 · סטטוס: ממתין לאישור הבעלים · לא בוצע implementation.

## 0. מה כבר קיים (inventory) — ומה נבנה עליו

| קיים היום | איפה | מה עושים איתו |
|---|---|---|
| הרשמות (`project_leads`) עם סטטוסים: new / approved / rejected / converted / pending / failed, `meta` (UTM, linking), `companyId`, `agreementId` | טאב "הרשמות", דוח הקמפיין, פעולות (תזכורת/שליחה מחדש/חידוש קישור/WhatsApp/העתקת קישור) + bulk | **ההזמנה מצטרפת לאותה טבלה** כרשומה עם `source='invitation'` וסטטוס `invited` — לא מודול לידים נוסף |
| אירועי קמפיין (`campaign_events`: page_view, cta_click, registration_completed…, visit id, UTM, referrer) | דוח הקמפיין (פאנל, מקורות, מבקרים ייחודיים) | "נכנס לקישור" = אירוע page_view עם מזהה ההזמנה ב-UTM המערכתי (`xs_inv`) — attribution בלי פרטים אישיים |
| הפצות (`distributions`, `distribution_recipients`, `message_sends` עם snapshot לכל שליחה, is_test, ok/error, provider id) | טאב "הפצות" (5 שלבים, Inforu SMS/Email) | **שליחת הזמנה אישית = הפצה של נמען אחד**; היסטוריית השליחות של הזמנה = שורות `message_sends` שלה |
| תבניות הודעות (invitation / reminder / registration_completed / signed_confirmation, משתנים, overrides לקמפיין, preview, test) | הגדרות → הודעות | ההזמנה האישית משתמשת בתבנית `invitation` עם `{{signing_link}}`→ הקישור האישי; WhatsApp מקבל את גרסת ה-SMS |
| WhatsApp share (`src/lib/whatsapp-share.ts`, wa.me עם טקסט מוכן, ללא API) | טבלת ההרשמות | אותו מנגנון + דיאלוג אישור ידני "כן/לא נשלחה" |
| מקור נתונים לקמפיין (`registration_target`: XTRA Sign / CRM) + resolver מחמיר | הגדרות → עמוד והרשמה | "הוסף כספק/לקוח" מההזמנה מכבד אותו, אותו resolver |
| Bulk בטבלת ההרשמות (בחירה → סרגל → תוכנית → אישור) | טאב "הרשמות" | מורחב לתגים/אחראי/משימת המשך; אותו pattern בספקים/לקוחות |
| חידוש קישור (`resume`), סטטוס קמפיין, closed page | — | הקישור האישי מפנה לאותו עמוד/טופס; פקיעה מתחדשת דרך קוד |
| **לא קיים:** תגים, אחראי לטיפול, תאריך חזרה, תוצאת שיחה, הערה פנימית להרשמה, משימות המשך, מעקב מסירה של Inforu (Pull) | — | נבנה בקטן, לפי הסעיפים למטה |

## 1. יצירת קמפיין — מסך מתוקן

שני מסלולי התחלה בלבד. שום יכולת לא נחסמת לפי המסלול; המסלול קובע ברירות מחדל ולשוניות.

```
 מה תרצו לעשות?
 ┌──────────────────────────┐   ┌──────────────────────────┐
 │  לאסוף פרטים מאנשים        │   │  להחתים אנשים על מסמכים    │
 │  טופס → פנייה מחכה לטיפול │   │  הסכם → קוד → חתימה → PDF │
 └──────────────────────────┘   └──────────────────────────┘
                     "מה ההבדל בין האפשרויות?"  (נפתח בלחיצה)
 למי מיועד?   ספקים │ לקוחות │ שניהם
 איך ייכנסו?  קהל קיים │ טופס ציבורי │ הטמעה │ API │ עמוד מותאם   (מוצג רק מה שרלוונטי)
 פרטים        שם · (למסמכים) ההסכם או "אעלה אחר כך"
```

* "שניהם" = `groups.kind = null` (כבר נתמך: המסננים מציגים ספקים ולקוחות).
* "קהל קיים" לא מחייב בחירה עכשיו — בוחרים בטאב "קהל". טופס ציבורי לא מחייב קהל. הפצה לעולם לא מחייבת.
* ה-`campaign_kind` הפנימי נשאר לדיווח/ברירות מחדל בלבד; הוא לא מסתיר כפתור.

### טבלת ההשוואה (מאחורי "מה ההבדל?")

| | איסוף פניות | החתמה על מסמכים |
|---|---|---|
| מה קורה אחרי הטופס | הפנייה מחכה לצוות (לאשר / להמשיך לחתימה ידנית) | הנרשם עובר ישירות להסכם, קוד וחתימה |
| צריך הסכם? | לא | כן (אפשר להעלות אחר כך) |
| קהל קיים | אפשר, לא חובה | אפשר, לא חובה |
| טופס / הטמעה / API / עמוד מותאם | כן | כן |
| הפצות SMS/Email | כן | כן |
| הזמנה אישית | כן | כן |
| דוחות | פניות, מקורות, נציגים | + חתימות, משימות המשך |

## 2. שליחת הזמנה אישית (הפעולה הראשית בכל קמפיין)

**כפתור:** "שליחת הזמנה" בראש הקמפיין (ליד "קמפיין חדש" יש "שליחת הזמנה" גם ברשימת הקמפיינים? לא — רק בתוך הקמפיין).

```
 שליחת הזמנה                                   ✕
 שם העסק / איש הקשר  [__________________]
 טלפון               [___________]   או  אימייל [______________]
 ערוץ                (●) SMS   ( ) אימייל   ( ) WhatsApp
                     תצוגה מקדימה: "שלום {{שם}}, נשלח אליך…"  (מהתבנית של הקמפיין)
                                             [ שליחה ]
```

* המערכת מייצרת **הזמנה** (`project_leads` עם `source='invitation'`, סטטוס `invited`, `invitedBy`, ערוץ) ו**קישור אישי יציב**: `https://<domain>/<slug>?xs_inv=<מזהה הזמנה>` — אותו עמוד/טופס של הקמפיין, בלי סוד, בלי פרטים אישיים ב-URL. ה-`xs_inv` נרשם ב-`campaign_events` (כניסה לקישור) וב-`meta` של ההרשמה כשמישהו נרשם דרכו.
* SMS/Email: נשלחים כהפצה של נמען אחד (Inforu) → `message_sends` (snapshot, provider id, ok/error). סטטוס שליחה אמיתי בלבד: נשלח / נכשל; "נמסר/נפתח/נלחץ" יוצגו רק כשייבנה Pull ל-Inforu (מסומן "הנתון עדיין לא זמין").
* WhatsApp: דיאלוג "מעבר ל-WhatsApp" → wa.me עם ההודעה → חזרה: "כן, ההודעה נשלחה" / "לא נשלחה". רק אישור מפורש = `sent_manual` עם מי ומתי; ניתן לתקן.
* מניעת כפילויות **לפני** השליחה: אותו טלפון/אימייל (לא שם) בקמפיין → הצג את המצב הקיים (הוזמן/נרשם/חתם) והצע "שלח שוב" / "תזכורת" / "פתח פרטים" במקום הזמנה חדשה.
* אם הנמען כבר ספק/לקוח (לפי מדיניות המקור של הקמפיין) — ההזמנה מקושרת אליו; לא נוצרת רשומה עסקית חדשה בשלב ההזמנה.

## 3. מודל נתונים (מינימלי, אדיטיבי)

* `project_leads` — עמודות חדשות: `invited_by` (משתמש), `invite_channel`, `assignee_user_id`, `follow_up_at`, `call_outcome` (interested / not_interested / call_back / no_answer), `internal_note`, `last_activity_at`. סטטוס חדש `invited` (לפני `new`). ההזמנה, ההרשמה וההסכם = **אותה שורה** לאורך כל המסע, כך שאין כפילות בין מודולים.
* `message_sends` — כבר מחזיק את היסטוריית השליחות; מוסיפים `lead_id` (השורה של ההזמנה) ו-`manual_confirmed_by/at` ל-WhatsApp.
* **סטטוס תהליך** (בשורה): הוזמן → נרשם → ממתין לחתימה → חתם. **סטטוס שליחה** (בהודעה): נשלח / נכשל / סומן כנשלח על ידי הנציג. שני צירים, בלי סתירה.
* תגים: `tags` (organization, name, color, kind: 'company' | 'campaign'), `company_tags`, `lead_tags` (תג קמפיין על הרשמה/הזמנה — לא מזהם את כרטיס החברה). ייחודיות לפי שם מנורמל בארגון.
* משימת המשך: `follow_up_tasks` (organization, group, lead/agreement/company, `kind` — למשרד התיירות: `site_product`, status: pending / in_progress / done / not_needed, assignee, due_at, note, link). הקמפיין מגדיר אילו משימות נוצרות אוטומטית אחרי חתימה (`groups.follow_up_config`). לא פרויקטים, לא לוחות.

* "רשימת מעקב" = מסנן "תאריך חזרה: היום ומוקדם יותר", עם באנר "N לחזור אליהם היום".

## 5. תגים ו-Bulk Edit (סגנון Shopify)

* תג מהכרטיס: שדה "הוסף תג" עם השלמה מהקיימים או יצירה; צ'יפים קומפקטיים בטבלאות (עד 2 + "+N"); מסנן תגים (AND/OR פשוט: "כל התגים" / "אחד מהם").
* Bulk: מסמנים → סרגל: **הוספת תגים | הסרת תגים | עריכה | שליחה | ייצוא**. הוספה/הסרה מפורשות (לא דריסה). "עריכה" = אחראי, סטטוס עבודה, תאריך חזרה, משימת המשך. **לא** ח.פ., מקור CRM, פרטי זהות. שרת: הרשאות, validation, audit, דיווח הצלחות/כשלים. אין כתיבה ל-Fireberry.

## 6. משימת המשך "הקמת מוצר באתר" (משרד התיירות)

* הגדרת קמפיין (הגדרות → מתקדם → "משימות המשך"): "אחרי חתימה: ליצור משימה ___" — למשרד התיירות: **הקמת מוצר באתר**. נוצרת אוטומטית עם החתימה (גם למי שכבר חתם — backfill חד-פעמי).
* בטבלה: עמודת סטטוס משולבת "חתם · ממתין להקמה" עם סימון ✓ מהיר; ב-Drawer: אחראי, תאריך יעד, הערה, קישור למוצר, "לא נדרש".
* מסננים ומספרים: **חתמו וטרם הוקמו** / **הקמה בטיפול** / **הוקמו באתר** — בקהל ובדוחות.

## 7. דוחות ו-attribution

* שורות KPI: הוזמנו · נשלחו (לפי ערוץ) · נכנסו לקישור · נרשמו · חתמו · הוקמו באתר. פילטרים: נציג, סטטוס, מקור, ערוץ, תגים, תאריכים, משימה.
* כלל attribution מתועד: **ההזמנה/ההפצה האחרונה שנפתחה לפני ההרשמה** (last-touch לפי `xs_inv`/מזהה הפצה), ואותה חתימה נספרת פעם אחת בדוח הכולל. פירוט "כל המגעים" ב-Drawer.

## 8. מה לא נבנה עכשיו

Pull של מסירה/פתיחה מ-Inforu (יסומן "הנתון עדיין לא זמין"), סנכרון תגים ל-CRM, ניהול משימות כללי, WhatsApp API.

## 9. סדר ביצוע (אחרי אישור)

1. Wizard + טבלת ההשוואה; "שניהם". 2. שליחת הזמנה + קישור אישי + WhatsApp אישור ידני + קהל מורחב עם Drawer. 3. תגים + Bulk. 4. משימת המשך + backfill למשרד התיירות. 5. שדות מעקב (אחראי/חזרה/תוצאה/הערה) + שליחת המשך עם זכאות. 6. דוחות + attribution. 7. QA (375–1440), Preview, פריסה מבוקרת.

Migrations: אדיטיביות בלבד. הקמפיין החי לא נוגע: כל היכולות מתווספות סביב הרשומות הקיימות.
